# 커스텀 UI (게임화 표면) — 리서치 종합 & 설계안 (2026-08-06)

Elyn JSX 심층 + RisuAI/SillyTavern 소스 레벨 조사(리서치 에이전트 2개) 종합. B7 백로그의 설계 근거 문서.

## 1. 조사 결과 요약

### Elyn JSX (2025-10-30 도입, 커뮤니티 가이드 기반 재구성)

- **저작**: 캐릭터 단위 "컴포넌트 코드 칸" + 프리뷰 에디터. **실제 React 함수형 서브셋** — 훅 화이트리스트(useState/useEffect/useMemo/useCallback/useRef, 접두사 없이 직접 호출), className·문자열 style 금지(인라인 객체만), setInterval/setTimeout 금지, 외부 npm 금지.
- **바인딩**: 상태의 진실 원천 = **모델 출력 그 자체**. 모델이 매 턴 답변 말미에 호출 코드(`<StatusWindow time=".." affection={55} />`)를 문자 그대로 출력 → 플랫폼이 감지·렌더. 첫 메시지에 초기값 호출 코드를 심고, 시스템 프롬프트에 "출력 규칙"으로 강제. 플랫폼 영속 변수({{getvar}}류)나 내장 변수 주입은 **발견되지 않음**.
- **인터랙션**: onClick으로 컴포넌트 내부 상태 조작(모달·아코디언·테마 토글)까지. 채팅 전송을 트리거하는 API는 확인 안 됨.
- **알려진 문제**: ① **출력 토큰 잠식이 최대 불만**("출력량 타노스") — 매 턴 전체 props 재출력 구조의 필연. ② 모델의 prop 오기입이 일상 → 방어적 에러 상태 내장이 저작 관행. ③ 보안 모델 미공개(iframe 아닌 메인 앱 내 제한 인터프리터로 추정).
- **생태계**: 사실상 표준화("JSX 없으면 별로"), AI로 컴포넌트를 깎는 워크플로(공식 Gemini 젬 + 인앱 도우미 봇), 코드는 포스타입 txt·디스코드로 유통. 실례: NpcStatus 상태창(9.3KB), 다인챗 호감도 게이지, 테마 전환(themeCode 매핑), 세계지도, 전투 시뮬 RPG.

### RisuAI / SillyTavern (소스 확인)

- **JS 전면 금지가 양 생태계 공통 결론** — RisuAI는 카드 내 임의 JS(virtualscript)를 보안 문제로 완전 폐기. 대신:
  - **editdisplay 정규식**: 모델이 압축 블록(`[status] 호감도=55 ...`) 출력 → IN 정규식 캡처 → OUT의 HTML/CSS 템플릿에 `$1` 바인딩. `@@move_top`(상단 고정), `@@repeat_back`(이번 턴 미출력 시 직전 상태 유지) 같은 액션.
  - **변수 시스템**: `{{setvar}}`는 전송 시점(runVar)에만 실행, 표시 경로에선 제거(rmVar) — 재렌더 멱등성 확보. 표시 트리거의 setvar는 tempVars 격리.
  - **인터랙션**: `{{button::라벨::트리거}}` → `risu-trigger` 화이트리스트 속성 → 이벤트 위임으로 엔진 콜백. "HTML은 선언만, 동작은 브리지" 패턴.
  - **CSS**: 문자열 필터가 아닌 **AST 재작성** — 셀렉터에 `.chattext` 접두 + 클래스 `x-risu-` 네임스페이스 + `@import` 차단, DOMPurify 2차. SillyTavern이 이 코드를 그대로 이식했을 만큼 검증됨.
  - **최종 방어선**: DOMPurify(스크립트·이벤트 핸들러 제거, href 프로토콜 화이트리스트, 클래스 네임스페이스).
- **임포트 호환**: V2/V3 카드의 `extensions.risuai.customScripts`(정규식+HTML 템플릿), `defaultVariables`, 에셋이 임포트 시 그대로 도착 — CBS 서브셋(`getvar/#if/#each/calc/button`)만 구현하면 커뮤니티 상태창 카드 다수를 렌더 가능.

## 2. SHIZUE 설계안 — 2계층

Elyn의 표현력(JSX)과 RisuAI의 안전 모델·변수 시스템을 결합하되, **우리 서버 상태(관계 스탯·에셋·세계관)를 1급 바인딩 소스로** 제공해 Elyn의 최대 약점(토큰 잠식·상태 비영속)을 해결한다.

### Layer 1 — 선언적 템플릿 + 변수 시스템 (Chunk 15, RisuAI 호환)

- **챗 변수 저장소**: `chats.variables jsonb` — `{{setvar::k::v}}/{{addvar::k::n}}`을 모델 출력 커밋 시점에만 실행(RisuAI runVar 시맨틱), 표시 시 매크로 제거. `card.defaultVariables` 지원(임포트 호환).
- **표시 스크립트(카드 필드)**: `displayScripts: {in(정규식), out(HTML 템플릿), order, actions(move_top|move_bottom|repeat_back)}` — 모델 출력 표시 시점에만 적용, 저장 데이터 불변. RisuAI `customScripts` 임포트 매핑.
- **템플릿 바인딩**: OUT 안에서 RisuAI CBS(중첩·`{{#if}}`·`{{#when}}`·`{{? }}`·`{{equal}}` 등, 프롬프트와 같은 `@shizue/core/cbs`) 확장 — `{{getvar::k}}`, `{{#each}}`, `{{calc}}`, `{{img::slug}}`(카드의 원래 그림 이름도), **플랫폼 변수** `{{rel::affection}}` 등 6축 관계 스탯·`{{turn}}`·`{{user}}`·`{{char}}`.
- **새니타이즈**: DOMPurify(허용 태그·속성 화이트리스트, on* 제거, href 프로토콜 제한) + `<style>` CSS AST 재작성(셀렉터 `.shizue-msg` 접두, 클래스 `x-shizue-` 네임스페이스, @import·외부 url() 차단 — 검증된 RisuAI/ST 패턴 이식).
- **인터랙션 1단계**: `{{button::라벨::입력텍스트}}` — 클릭 시 해당 텍스트를 입력창에 채움(전송은 유저가) → 선택지 UX를 안전하게.
- 효과: 상태창·게이지·테마 카드가 즉시 가능 + **RisuAI 카드 임포트 시 상태창 자동 재현** (경쟁사 전무 기능).

### Layer 2 — 샌드박스 JSX 컴포넌트 (Chunk 16, Elyn 스타일 상위 호환)

- **저작**: 캐릭터당 컴포넌트 코드 필드(프리뷰 에디터 포함). Elyn과 동일한 서브셋 규칙(훅 화이트리스트, 인라인 스타일, 타이머·npm 금지) — **Elyn에서 유통되는 컴포넌트 코드가 거의 그대로 동작**하는 것을 호환 목표로.
- **실행 격리 (Elyn과의 차별)**: 메시지 인라인 **sandboxed iframe**(`sandbox="allow-scripts"`, 별도 오리진 없음, CSP로 네트워크 차단 — 이미지 등 외부 로드는 프록시 경유 허용 목록) + postMessage 브리지. 앱 DOM·쿠키·API 접근 원천 차단 — Elyn의 미공개 보안 모델보다 구조적으로 안전.
- **바인딩 2원화**:
  - (a) Elyn 호환: 모델이 출력한 호출 코드의 props 파싱 → 컴포넌트 전달
  - (b) **플랫폼 변수 주입(우리 개선)**: Layer 1 변수 + 관계 스탯 + 에셋 URL 맵을 브리지로 자동 주입 — 모델은 `{{setvar}}` 델타만 출력하면 되므로 **Elyn의 토큰 잠식 문제 해소**
- **인터랙션 브리지**: 컴포넌트 → `postMessage({type:'suggestInput', text})` 화이트리스트 이벤트만(입력창 채움). 그 외 무시.
- **방어 규칙 내장**: prop 누락·오기입 기본값 처리를 저작 가이드로 강제(Elyn 커뮤니티 교훈), 컴포넌트 에러 시 해당 iframe만 폴백 표시.

### 순서 권장

Layer 1 → Layer 2. Layer 1은 임포트 호환·변수 인프라(2계층이 재사용)·즉효 게임화를 한 번에 주고 위험도가 낮다. Layer 2는 Layer 1의 변수·에셋 브리지를 재사용한다.

## 3. 해외 조사 결과 (2026-08-06 추가)

### 결론: Elyn급 "크리에이터 저작 UI"는 해외에 사실상 없다

- **Chub.ai Stages가 유일한 근접 사례** — 하지만 진짜 React+TS 앱을 로컬 빌드→GitHub CI로 배포하는 **개발자용 플랫폼**. 기술적으론 우리 설계보다 앞선 부분도 있으나(하단), 저작 장벽 때문에 **공개 스테이지 총 26개**로 생태계가 얇고, 그 간극을 "Statosphere"(JSON 설정으로 변수·수식·분류 규칙을 정의하는 노코드 메타 스테이지)가 메우고 있음 → **선언형 레이어가 실수요라는 강력한 증거 = 우리 Layer 1 우선 전략의 타당성 입증**.
- AI Dungeon: 크리에이터 JS(훅 3종, 서버 샌드박스 16MB/2초, 사후 모더레이션) — 로직만, UI 렌더 불가. Plot Card CRUD API를 가변 DB로 쓰는 문화.
- Perchance/OpenCharacters: 풀 JS + `oc` API(버튼이 유저 메시지 직접 전송, 커스텀 패널, 코드 내 LLM 호출) — 가장 개방적, 격리는 iframe에 전적 의존.
- 서구 상용 나머지: 모바일(Talkie/Replika)은 플랫폼 소유 가챠·XP뿐, 웹 RP(Janitor/Spicy)는 프로필 CSS만 — 채팅 상태창은 순수 프롬프트 문화(수요는 봇·가이드 유통으로 확인). **선언형 템플릿 중간 사다리가 통째로 공백**.
- 표준 부재: CCv3는 `.lua/.js` 보관 위치만 정의하고 실행 시맨틱스는 미정의. 유일한 수렴 신호는 **MCP**(Chub SDK 0.5.x McpServer 내장, RisuAI 모듈 mcp 필드) — "카드 = LLM 툴 제공자" 방향.

### Chub Stages에서 가져올 설계 요소

1. **메시지 노드 단위 상태(messageState)** — 스와이프/브랜치 점프 시 그 노드의 상태로 복원. 트리 채팅의 상태 정합성 문제를 플랫폼 계약으로 해결한 유일 사례 (ST 확장들의 공통 난제).
2. `StageResponse` 훅 표면: `stageDirections`(비영속 프롬프트 주입)·`systemMessage`(모델이 따라하지 않게 시스템 메시지로 표시)·`modifiedMessage`.
3. `chub_meta.yaml` config_schema → 설정 UI 자동 생성.
4. 별도 도메인 iframe + postMessage origin 이중검증, 스테이지별 서브도메인 분리.

### 우리 설계 보강 (리드 결정)

- **변수는 경로 파생(path-derived)으로**: Layer 1의 챗 변수를 별도 컬럼에 저장하는 대신, **현재 브랜치 경로의 메시지들을 순서대로 접으며 `{{setvar}}` 매크로를 재생해 계산**한다. 우리 append-only 트리 덕에 Chub messageState와 동일한 브랜치 정합성을 저장소 0으로 얻는다 — 스와이프/포크 시 상태가 자동으로 그 분기 기준이 됨. (성능: 경로당 1회 파싱, head 기준 캐시.)
- **저작 사다리 3단**: ① 프리셋 템플릿 갤러리(상태창·게이지 완성품 고르기 — 노코드) ② Layer 1 선언형 ③ Layer 2 JSX. Chub의 교훈: 최상단만 있으면 생태계가 안 자란다.
- **뷰어 보호**: 커스텀 UI 표시 opt-out 설정 + 플레인 텍스트 폴백(JanitorAI 교훈), 새니타이저 규칙 변경 시 하위호환 테스트 스위트(기존 자산 파손 방지 = 크리에이터 신뢰).
- Layer 2 훅 표면은 Chub 서브셋으로: 렌더 + (후속) stageDirections류. impersonate/nudge 같은 능동 개입은 도입 보류(안전 검토 후).

## 4. 구현 결과 (2026-08-06 완료)

Layer 1 `12cb556`, Layer 2 `e5ecc8d`. 서 있는 구조는 이렇다:

- **실행 렘은 iframe 안의 Worker다.** 불투명 출처는 출처 경계일 뿐 내비게이션·CPU 경계가 아니다 — iframe만으로는 창작자 코드가 `Function('return location')()`로 프레임을 이동시켜 URL에 플랫폼 상태를 실어 보내거나(`connect-src`는 내비게이션을 통제하지 않는다), WebRTC ICE로 은닉 채널을 열거나, `while(true)`로 탭을 얼릴 수 있다. 그 안의 워커가 셋을 닫는다: 이동할 문서도 `RTCPeerConnection`도 없고 `terminate()`가 가능하다 — 차단이 아니라 부재로 해결.
- 그래서 **워커가 보내는 트리가 신뢰 경계다.** 프레임의 신뢰 코드가 그리기 전에 전체 트리의 형태·노드 수(5000)·깊이(64)를 검사하고, 이벤트 이름은 화이트리스트, `href`/`ping`/`target` 등 내비게이션 속성은 무조건 제거한다(상태를 쥔 프로그램이 링크를 합성해 유출하는 것을 막는다).
- **감시 타이머는 출력이 아니라 응답성으로 해제**한다. 렌더 후 ping을 보내고 pong이 와야 데드라인이 풀린다 — 루프에 빠진 워커는 가짜 트리는 보낼 수 있어도 답할 수 없다.
- 부모↔프레임은 창작자 코드가 존재하기 전에 넘긴 MessagePort로만 통신하고, 두 번째 `load`(자기 내비게이션)에서 프레임을 폐기한다.

**하드닝 추가 (Phase 0B, 게임 레이어와 동일 레인)**

- 워커 부트 시 `postMessage`를 클로저로 캡처한 뒤 전역 프로퍼티를 undefined로 덮는다. 채널이 런타임의 사유물이 되므로 `Function('return postMessage')()`로 브리지 메시지를 위조할 수 없다 — `sendTurn`이 그 메시지 중 하나가 된 이상 필요한 조치.
- `checkTree`가 `attrs/style/props/on/children` 부재를 빈 값으로 채운다. 타입이 틀린 필드는 여전히 거부. "잘못된 트리는 문서를 절반만 그린 채 남기지 않는다"는 주석이 실제로 참이 됐다(희소 노드가 patch 중간에 TypeError를 내던 경로 제거).

### 4.1 잔여 리스크 레지스터 (2026-08-07 갱신)

출시 시점에 "수용, 문서화"로 남겼던 넷을 전부 닫았다. 닫은 방식과, 그 대가로 새로 생긴 것들.

**닫음 — Layer 1 정규식은 이제 중단할 수 있다.**
저작 시점 검사(`@shizue/core/display-script`)를 더 조이는 길은 포기했다. 그 검사는 *괄호 그룹*만 본다: `\[status\] hp=\d+ a+a+a+a+a+a+a+a+a+a+b`에는 볼 그룹이 아예 없고, 문자 클래스 연쇄는 모듈 주석이 명시적으로 합법이라고 선언한 형태이며, `(a|aa){1,20}`은 유계 수량자라 `isUnbounded`가 아무 말도 하지 않는다 — 셋 다 스캔 대상 줄 길이에 지수적이고 셋 다 통과한다(계측: 26자 21.5ms, 두 자마다 배증). 일반해는 정규식 모호성 분석이고, 그것을 피하려고 만든 검사에 그것을 넣을 수는 없다. **그래서 정규식이 도는 자리를 옮겼다** — Layer 2가 창작자 코드에 내린 것과 같은 결론이다.
- **매칭만** `apps/web/src/lib/displayPlanner.ts`의 워커로 갔다. 워커는 `terminate()`가 되고, 1,000ms(내부 협조적 예산 50ms의 20배) 안에 답이 없으면 스레드를 끝내고 그 메시지는 평문으로 그린다. 나머지 요청은 새 스레드가 받는다.
- **렌더는 남았다.** DOMPurify가 신뢰 경계이고 워커에는 DOM이 없다. 렌더 쪽은 고정 패턴만 쓰므로 정지하지는 않지만, **양이 유계는 아니었다** — 그리고 분할이 처음 만들었던 구멍이 정확히 여기였다. 옛 코드의 50ms 데드라인은 매치 *사이*에서 검사됐으므로 렌더 쪽도 같이 묶고 있었는데, 분할 직후의 예산은 **살아남은 출력**(`MAX_HTML_CHARS`)만 셌다. 새니타이즈는 비싼 입력을 *버리는* 단계다: 속성 화이트리스트가 거부하는 선언으로 채운 89KB `<style>`은 매치마다 CSS 파스를 시키고 8자로 돌아오므로, 카운터가 100,000분의 800에 앉아 있는 동안 메인 스레드가 8.5초 멈춘다(계측).
  - 그래서 **일하기 전에 청구한다**(`MAX_RENDER_INPUT_CHARS`, 100,000). 매치마다 ① 파스하려는 템플릿 길이 ② 새니타이저에 넘기려는 문자열 길이를 각각 그 단계 *이전에* 청구한다. ②가 반대 형태(한 줄짜리 템플릿이 `{{#each}}`로 70KB를 뱉고 전부 버려지는 경우)까지 잡는다. 출력 캡은 그대로 둔다 — 다른 것을 묶는 캡이다.
  - 값이 100,000인 이유: 이웃 둘(`cbs`의 중간 캡, 출력 캡)과 같은 숫자여서 셋을 한 번에 기억할 수 있고, 가장 비싼 종류의 입력이 청구 문자당 약 0.5µs이므로 옛 50ms 데드라인을 문자로 환산한 값과 대체로 같다. 계측: 적대적 케이스 8,477ms → **0ms**(평문 폴백), 평범한 무거운 메시지(작은 상태창 100개)는 37ms로 전부 그려진다.
  - **예산은 단계 하나가 아니라 렌더 전체를 관통한다.** "출력을 재지 말고 입력을 먼저 청구하라"는 규칙은 한 번 적용해서 끝나지 않았다 — 캡처 치환도, 템플릿 엔진도 각각 "많이 쓰고 조금 돌려주는" 단계였다.
    - **캡처 치환**: 예산 안에 들어오는 템플릿 하나가 `$1`을 5만 개 담을 수 있고 캡처는 2만 자까지 가능하다. 결과 문자열을 재려면 먼저 그 문자열(수억 자)을 만들어야 한다 — 2만 참조에서 5,703ms, 5만 참조에서는 힙이 터진다. 그래서 `bindCaptures`가 **치환할 때마다** 청구하고, 예산이 떨어지는 순간 `replace` 안에서 던진다. 만들어지는 것은 지불된 것뿐이다. → **2ms**.
    - **CBS 확장이 아무것도 안 남기고 끝나는 경우**: `{{getvar::blob}}` 한 줄이 5MB 변수를 이스케이프하다 엔진 내부 문자 캡에 걸려 던지면, `renderTemplate`이 그걸 잡아 **작은 이스케이프된 원본**을 돌려줬다. 호출자는 30자를 청구하고 다음 매치에 같은 값을 또 산다. 99매치 × 5MB = **14,282ms**. 두 군데를 고쳤다: ① 동적 값은 **확장 전에** 길이로 청구한다(`read()` — getvar·calc·`{{#if}}`·`{{#each}}`·`{{slot}}`·char·user·img 전부 이 문 하나를 지난다) ② **예산 소진은 삼키지 않고 호출자에게 던진다**(`RenderBudgetExhausted`). 파서가 거부한 템플릿은 예전처럼 이스케이프된 원본으로 돌아온다 — 창작자의 오타는 보여야 하고, 예산 소진과 혼동되면 안 된다. → **1ms**. `{{#each}}` 14,519 → 1ms, `{{calc}}` 14,426 → 0ms, `{{#if}}` 82 → 0ms, `repeat_back` 캐리오버도 같은 경로라 같이 닫혔다.
    - 규칙을 한 문장으로: **어떤 단계도 아무도 청구하기 전에 쓰지 않는다.** `stripTaint(script.out)`조차 템플릿을 한 번 훑으므로 청구가 그 앞으로 갔다.
- 이 절단면은 **데이터가 갈라지는 자리와 같다**. 계획(어디에 매치가 있는가)은 메시지 텍스트·스크립트·직전 메시지에만 의존하고 셋 다 스트리밍이 끝나면 불변이다. 바인딩(`{{getvar}}`·`{{rel}}`·`{{turn}}`)은 계획에 들어가지 않으므로, 변수가 바뀌면 이미 손에 든 계획 위에서 **왕복 없이 동기 재렌더**된다. 게이지는 예전과 똑같이 즉시 움직인다.
- 대가 ①: **정착한 메시지는 계획이 도착하기 전 한 프레임 동안 평문으로 보인다**(워커 왕복 1회). 대가 ②: **스트리밍 중인 메시지에는 표시 스크립트를 아예 적용하지 않는다** — 반쯤 쓰인 상태 블록은 상태 블록이 아니고, 매 토큰마다 자라는 문자열을 다시 매칭하는 것은 틀린 동시에 낭비였다. 이건 회귀가 아니라 의도한 동작 변경이다.
- 검증: 실제 스레드에서 위 패턴을 돌려 1,000ms 후 종료되고 메인 스레드는 그동안 계속 돌았음을 확인한다(`apps/web/test/displayPlannerThread.test.ts`). 프로덕션 번들에서 `planDisplayScripts.toString()`이 여전히 자립 함수인 것도 확인했다(minify 후 추출해 빈 렘에서 실행).

**닫음 — `href`는 이제 최종값으로 판정한다.**
템플릿 모양을 믿는 대신, 보간된 값에 표식을 달아 새니타이저가 **완성된 `href`**를 보고 결정한다(`apps/web/src/lib/taint.ts`). 표식은 모델이 고른 것에만 붙는다: `{{getvar}}`·`{{calc}}`/`{{? }}`·`{{slot}}`·정규식 캡처(`$1`), 그리고 표식 있는 인자를 읽은 RisuAI 함수(`equal`·`random` …)의 결과. `{{char}}`·`{{user}}`·`{{turn}}`·`{{rel}}`·`{{img}}`는 우리가 만든 값이라 붙이지 않는다 — 붙이면 멀쩡한 링크만 죽는다.
- 판정 결과는 **거부가 아니라 무력화**다. `<a>`는 라벨을 유지한 채 `href`/`target`/`rel`을 잃고, 갈 뻔했던 주소가 그 옆에 평문으로 찍힌다(120자 절단). 통째로 지우면 "카드가 어딘가로 보내려 했다"는 사실 자체가 사라지는데 그게 독자가 알아야 할 것이고, 클릭 가능한 채로 두면 낯선 자가 고른 라벨 뒤에 낯선 자가 고른 오리진이 클릭 하나 거리에 남는다. 둘 다 아닌 것이 답이다.
- 모델이 표식 문자(U+0001)를 변수에 심어도 소용없다. 값은 들어올 때 표식이 제거된 뒤 우리 표식이 다시 붙고, 애초에 표식을 위조하면 *더 많이* 오염될 뿐이다 — 판정은 링크를 거부하는 쪽으로만 실패한다.
- 정적으로 창작자가 써 넣은 링크는 예전 그대로 새 탭·`rel="noopener noreferrer nofollow"`로 열린다.

**닫음 — 도는 컴포넌트는 이제 회수된다.**
프레임이 5,000ms마다 유휴 워커에 ping을 보낸다. 답이 없으면 기존 500ms pong 데드라인이 워커를 `terminate()`하고 늘 쓰던 폴백 카드를 세운다. 턴이 진행 중이면(데드라인이 이미 서 있으면) 그 틱은 아무것도 하지 않는다 — 안 그러면 5초마다 데드라인을 새로 깔아 영원히 죽지 않는다.
- 5초인 이유: 아래로는, 살아 있는 컴포넌트에 드는 비용이 5초에 postMessage 왕복 한 번이고 백그라운드 탭에서는 브라우저가 타이머를 분당 1회 수준으로 조인다(늦은 틱은 늦은 질문일 뿐 오탐이 아니다). 위로는, 회수 대상이 코어 하나를 태우는 스레드라 피해가 분 단위로 쌓이므로 초 단위 발견이면 이미 충분히 빠르다. 더 짧게 잡으면 얻는 것 없이 페이지의 모든 유휴 상태창에 값을 치른다.

**닫음 — 새니타이저에 회귀 게이트가 생겼다.**
`apps/web/test/sanitizeCorpus.ts` + `sanitizeCompat.test.ts`: 실제 유통 형태의 카드 12종(상태창·게이지·테마 카드·표·에셋 이미지·`url()` 배경·선택지 버튼·details/progress/meter·외부 링크·RisuAI 임포트 2종·산문 장식)을 **출력 고정**으로 박았다. `pnpm test`에 그대로 들어간다. `sanitizeHtml.test.ts`가 "죽어 있어야 할 벡터"를 지키는 반대쪽 절반이고, 둘이 같이 있어야 규칙을 조이는 변경과 푸는 변경이 각각 걸린다. 코퍼스를 지워 통과시키는 것을 막으려고 "이 코퍼스가 여전히 무엇을 덮는가"도 함께 검사한다.

**이번에 발견해 같이 고친 것.** 새니타이저 자신의 `URL_FUNCTION`이 `url(` 뒤 공백 런에서 이차 이상으로 폭발했다(공백 2,000자 1.4초, 8,000자 81초). 템플릿 출력 상한이 100,000자이므로 카드가 도달할 수 있는 값이었다 — Layer 1의 정규식을 워커로 옮기면서 바로 옆에 같은 종류의 정지를 남겨둘 수는 없어 패턴을 모호성 없는 형태로 다시 썼다. 인용부호 검사는 코드로 내려갔고, 코퍼스 출력은 한 글자도 바뀌지 않았다.

**아직 열려 있는 것.**
- **실제 브라우저 `Worker`로 도는 Layer 1 경로에는 E2E가 없다.** jsdom에는 `Worker`가 없어 단위 테스트는 Node 워커 스레드로 같은 소스를 돌려 종료를 증명한다. Layer 2의 `apps/e2e/tests/customUi.spec.ts`에 있는 "끝나지 않는 컴포넌트" 케이스의 Layer 1 판을 추가할 것.
- **`{{button::라벨::$1}}`의 채움 텍스트는 모델이 고를 수 있다.** 입력창에 들어갈 뿐 전송은 사람이 하므로 수용하지만, 표식이 붙는 값이 `data-shizue-fill`로도 흐른다는 것은 사실이다.
- **하트비트는 "도는 것"과 "정직하게 오래 걸리는 것"을 500ms 너머로 구분하지 못한다.** 턴 밖에서 워커가 계산하고 있을 이유가 지금 런타임에는 없으므로 실무상 문제가 아니지만, 훅 표면이 늘어나면 다시 볼 것.
- 표시 스크립트 계획 요청은 **한 번에 하나씩** 처리한다. 멈춘 요청을 특정하기 위한 선택이고 정상 경로에서는 마이크로초 단위지만, 메시지가 수백 개인 챗의 첫 페인트에서는 마지막 메시지의 계획이 그만큼 늦게 온다.
- **렌더 예산은 메시지당이다.** 메시지 N개는 N배를 쓰고, 첫 페인트에서는 그게 한 React 패스 안에 들어온다. 분할 이전에도 같은 형태였고(옛 데드라인도 메시지당 50ms였다) 이번 변경이 만든 것은 아니지만, 페이지 단위 상한은 여전히 없다.
- **서버는 카드가 실어 보내는 것에 길이 제한을 두지 않는다.** `coerceDisplayScripts`는 `in` 패턴만 검사하고(`apps/api/src/card.ts`), `coerceVariables`는 값 길이를 보지 않는다 — 89KB짜리 `out`도, 5MB짜리 `defaultVariables` 값도 지금 그대로 저장되고 임포트로도 들어온다. 클라이언트 예산이 있어 치명적이지 않지만, 지금은 클라이언트가 혼자 지고 있는 부담이다. API 레인에 넘길 구체 수치는 §4.2.

### 4.2 서버가 같이 져야 할 상한 (API 레인 몫)

클라이언트는 이제 렌더 예산으로 스스로를 지키지만, 그건 **모든 독자의 탭에서 매번** 치르는 방어다. 저작·임포트 시점에 한 번 거절하면 그 비용이 사라진다. `apps/api/src/card.ts`에 아래를 제안한다 — 전부 `badRequest('invalid_request', …)`로 거절(절단 아님: 카드는 왕복 후 바이트 동일해야 하고, 조용히 잘린 템플릿은 깨진 상태창으로 보인다).

**`coerceDisplayScripts`**

| 대상 | 제안값 | 근거 |
|---|---|---|
| `out` 길이 (스크립트당) | **20,000자** | 코퍼스에서 가장 큰 실제 카드가 1.3KB다. 15배 여유. 클라이언트 렌더 예산이 100,000이므로 이 상한이면 한 메시지에 큰 템플릿 5개가 여전히 들어간다. |
| 스크립트 개수 (카드당) | **64개** | RisuAI 임포트 실물이 보통 한 자릿수. 개수 상한이 없으면 `repeat_back` 스크립트 수천 개가 각각 캐리오버 매치를 만든다. |
| `in` 길이 | 이미 500 (`MAX_DISPLAY_PATTERN_LENGTH`) | 변경 없음. |

**`coerceVariables`** (`defaultVariables`, 임포트 경로 포함)

| 대상 | 제안값 | 근거 |
|---|---|---|
| 값 하나의 길이 | **10,000자** | 상태창 변수는 숫자·짧은 라벨·쉼표 목록이다. 클라이언트 렌더 예산(100,000)보다 한 자릿수 작아야 한 매치가 예산을 통째로 먹지 않는다. |
| 키 개수 | **256개** | |
| 전체 직렬화 크기 | **256KB** | 개수 × 길이 곱이 카드 크기를 지배하지 않게. |

주의: `{{setvar}}`로 **런타임에** 생기는 변수는 이 상한 밖이다(모델 출력에서 접히므로 메시지 길이에 종속된다). 그쪽은 클라이언트 예산이 계속 유일한 방어이고, 그래서 `read()`가 필요하다 — 서버 상한이 생겨도 지우면 안 된다.

## 5. 확인 못 해 자체 결정한 것들

Elyn의 파서 구현·컴포넌트 칸 상한·호출 코드 인식 문법·fetch 허용 여부는 미확인 — 우리 설계는 이에 의존하지 않고, 호환 목표는 "커뮤니티 유통 컴포넌트 코드가 큰 수정 없이 동작"하는 수준으로 잡는다. 정확한 문법 차이는 Layer 2 구현 시 대표 유통 코드(NpcStatus 등 공개 txt)로 테스트한다.
