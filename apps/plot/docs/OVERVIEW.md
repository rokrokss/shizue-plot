## 1. 메시지 하나가 지나가는 길

출처 표시: **[Risu]** RisuAI와 똑같이, **[ST]** SillyTavern과 똑같이, **[우리]** 우리가 더한 것.

독자가 기다리는 부분:

1. **독자가 메시지를 보낸다.** 캐릭터 대사를 대신 쓰거나(`@이름:`) 내레이션을 쓸(`@:`) 수도 있다. [우리]
2. **저장하기 전에 카드 규칙으로 다듬는다.** 카드의 정규식 스크립트와 매크로를 그 작품이 온 앱의 방식대로 적용한다. ST 카드는 입력·출력·화면·프롬프트 배치를, RisuAI 카드는 카드와 모듈의 정규식을 `<order N>` 순서로 따른다. [Risu] [ST]
3. **로어북에서 지금 필요한 설정을 찾는다.** 최근 대화에 키 단어가 나오면 그 항목이 켜진다. 어떤 항목이 켜지는지는 RisuAI·ST 규칙 그대로이고, 키워드로 켜진 항목을 보내는 자리만 독자 입력 뒤로 옮겼다(5장). 영어 작품은 가져올 때 보조 모델이 키마다 한국어 별칭을 만들어 둔다. 원래 키는 건드리지 않고 내보내기에도 넣지 않는다. [Risu] [ST] [우리]
4. **기억을 꺼낸다.** 요약(HypaV3), 요약에서 뽑은 사실, 그리고 켜 둔 경우 과거 메시지 검색. 찾을 때는 뜻 검색(KURE-v1 임베딩)과 글자 검색(BM25)을 합친다. 바뀐 옛 사실은 "종료"로 표시해 보내지 않는다. 그룹 작품에서 캐릭터는 자기가 없던 장면의 비공개 사실을 받지 않는다. [Risu] [ST] [우리]
5. **프롬프트를 조립한다.** 잘 안 바뀌는 것은 앞에, 이번 턴에만 쓰는 것은 독자 입력 뒤 한 메시지에 모은다(2장). [Risu] [ST] [우리]
6. **모델이 답한다.** 챗에 묶인 모델 프리셋으로 답을 받는다. 프리셋은 PocketRisu처럼 모델 레지스트리의 프로필에서 만든다 — 프로필은 모델마다 보낼 수 있는 칸과 기본값, 응답 상한, 상태를 정해 두어서 그 모델이 거절하는 값은 가지 않고, 생각하는 모델의 응답 상한은 생각까지 넉넉하며(Gemini 3.8 Flash 8192, Gemini 4 Argon 32,768), 구형·지원이 끝난 모델은 기본으로 숨는다. 레지스트리에 없는 것(ChatGPT 요금제, 로컬 서버, Bedrock·Vertex 등)은 형식과 모델 id를 직접 적는 커스텀 프리셋이다. 프리셋은 소유자의 ChatGPT 요금제(Shizue 확장으로 연결), API 키(OpenAI·Anthropic·Gemini·OpenRouter·Mistral·Cohere·NovelAI 같은 곳 — AWS Bedrock은 AWS 키, Vertex AI는 서비스 계정), 키 없는 로컬 서버(Ollama·text-generation-webui·KoboldCpp·LM Studio 등), AI Horde 가운데 하나로 돈다. 형식은 RisuAI의 요청 형식 전부다(RisuAI 페이지 안에서만 도는 WebLLM·플러그인은 빼고). 챗마다 메인과 보조를 따로 고르고, 고르지 않으면 설정의 기본을 따른다. [Risu] ChatGPT 경로의 대화 요청에는 대화 id로 된 캐시 이름을 붙인다. 독자가 화면을 닫아도 서버는 답을 끝까지 받아 저장한다. [우리]
7. **답을 다듬어 저장하고 그린다.** 카드의 출력 규칙, 화면 스크립트, 상태창, 음악, 토글을 그 앱에서처럼 그린다. 카드의 HTML은 RisuAI가 들이는 것을 들인다 — SVG 아이콘과 게이지, `data-*`로 고르는 스타일, 입력칸·드롭다운·슬라이더, 유튜브 영상. 다만 폼은 아무 데도 보내지 못하고, 다른 호스트의 그림·글꼴과 유튜브 밖의 프레임은 여전히 막는다. 카드 스크립트가 캐릭터를 고쳐 쓰면(이름·설명·첫 메시지·배경) RisuAI처럼 작품 자체에 남아 그 작품의 모든 대화가 읽는다. [Risu] [ST]

답이 끝난 뒤 백그라운드에서:

8. **기억을 정리한다.** 원문이 자리를 넘치면 오래된 메시지를 6개씩 요약하고, 같은 묶음에서 사실을 뽑는다. 여러 묶음을 몰아서 하고 한 턴에 함께 반영한다(4장). [Risu] [우리]
9. **작품을 가져올 때 별칭을 만든다.** 항목 210개짜리 책도 보조 모델 7번 정도면 끝난다. [우리]

## 2. 프롬프트 순서

요청은 **RisuAI·PocketRisu가 짜는 그대로**다. 프리셋이 정한 순서대로 블록을 놓는다. 기본 프리셋은 PocketRisu의 "Default Prompt"(OAI2)이고, 챗에서 내 프리셋을 고르면 그것이 통째로 대신한다(PocketRisu에서 프리셋을 바꾸는 것과 같다). 기본 프리셋으로 가는 요청은 위에서 아래 순서다.

| 순서 | 무엇 | 다음 턴에 |
|---|---|---|
| 1 | **시스템 프롬프트**: OAI2 규칙, `[Roleplay Setting]` 캐릭터 설명(+작품 설명), `[{{user}} Character Profile]` 페르소나, 상시 로어, 글로벌 노트 자리, 작가 노트 | 재사용 |
| 2 | **시스템 프롬프트**: `[Roleplay Summary]` 요약 중 중요 표시·최근 것 | 요약이 들어올 때만 바뀜 |
| 3 | **시스템 프롬프트**: OAI2 응답 지침, 말하는 규칙(멤버 하나 작품만), 나레이션 규칙 | 재사용 |
| 4 | **대화 기록**: 예시(블록마다 `[Start a new chat]`과 `example_user`·`example_assistant` 턴), `[Start a new chat]`, 대화 (깊이 로어 포함) | 재사용 |
| 5 | **독자의 최신 입력** | 다음 턴부터 재사용 |
| 6 | **이번 턴 묶음** (한 메시지): 말하는 규칙 한 줄, 내레이터·연출 지시, 키워드로 켜진 로어, 이번 턴 지시, 이번 턴 기억(비슷한·무작위 요약, 사실, 과거 메시지), 깊이 0 로어, 마무리 지시, OAI 탈옥 문구(탈옥 토글을 켰을 때만) | 매 턴 새로 |

- **우리가 더하는 것**: 말하는 규칙(`이름:` 줄 — 화면이 말풍선과 나레이션 상자를 나누는 근거, 제타식), 이번 턴 기억, 작품의 내레이터·연출 지시와 게임 판정, 답장 언어 줄. RisuAI에는 이것들의 자리가 없어 이번 턴 묶음에 둔다. 이 밖에 우리가 더하는 지시는 없다 — OAI 탈옥 문구도 기본 프리셋의 한 항목이라, 다른 프리셋은 제가 정한 대로 보낸다.
- **탈옥은 토글이다.** RisuAI의 `jailbreakToggle`처럼 기본은 꺼져 있고, 프리셋의 탈옥 항목과 탈옥 글은 챗 설정의 토글 칸에 있는 탈옥 토글을 켰을 때만 간다. 값은 작품의 전역 변수로 남는다(로컬 토글을 켠 챗은 그 챗의 것).
- **프리셋의 나머지 RisuAI 설정도 RisuAI처럼 읽는다.** `promptSettings`(`sendName`, `sendChatAsSystem`, `trimStartNewChat`, `postEndInnerFormat` 등), ChatML 항목, `{{position::이름}}` 자리, 프리셋 정규식(카드의 스크립트보다 먼저 보내는 글에 돈다), 이어 쓰기의 `[Continue the last response]`, 응답의 `<Thoughts>` 떼기, `{{asset_prompt::}}` 그림. RisuAI 프리셋을 가져오면 `promptSettings`와 프리셋 정규식도 함께 온다(편집 칸은 아직 없다).
- **`cache` 항목은 Claude의 캐시 지점이다.** RisuAI처럼 그 항목 앞의 턴에 캐시 표시를 달고, Anthropic 프로필 프리셋의 요청이 그 자리에 `cache_control`을 붙인다. 다른 제공자는 표시를 읽지 않는다.
- **여러 멤버 작품**은 RisuAI의 그룹챗 그대로다. 말하는 화자의 카드만 설명에 넣고, 다른 멤버의 답장은 `<이름's Message>`로 감싸 보내며, 끝에 `[Write the next reply only as 이름]`이 붙는다.
- **OAI2는 템플릿이라** RisuAI처럼 카드의 시스템 프롬프트를 읽지 않고, 시작 트리거의 `start`·`historyend` 주입도 갈 곳이 없어 보내지 않는다. 카드의 post-history 지시는 글로벌 노트 자리에 간다. 템플릿이 없는 프리셋(RisuAI 기본 순서)을 고르면 둘 다 RisuAI처럼 간다.
- **모델이 읽는 우리 글은 모두 영어다.** OAI2와 OAI 탈옥 문구는 PocketRisu 원문 그대로이고, 소유자가 뺀 문장(SFW 선호, 사용자 대필 금지)은 빠진 채다. 답장 언어는 기본 프리셋이 말하지 않는다 — 작품과 독자의 언어가 다르면 언어 모드가 맨 끝에 `[Reply language]` 줄을 붙인다. 영어 지시와 OAI2 기본이 답장 언어·거절률·글의 질에 주는 차이는 아직 재지 않았다.

왜 이 순서인가:

- **매 턴 바뀌는 것은 전부 맨 뒤 한 메시지에.** 이 경로의 캐시는 앞 요청에서 마지막 메시지만 뺀 것을 통째로 재사용한다(3장). RisuAI의 기본 순서도 로어·글로벌 노트·작가 노트를 가장 새 입력 뒤에 두므로 이미 그 모양이다. 조립기는 6을 항목별 system 턴으로 두고, ChatGPT 어댑터가 보낼 때 하나의 developer 메시지로 잇는다.
- **품질은 그대로.** 이번 턴 기억을 입력 앞과 뒤에 둔 12개 장면, 키워드 로어를 시스템과 입력 뒤에 둔 14개 장면을 실제 모델로 비교했고 차이가 없었다(6장).
- **RisuAI·ST와 다른 점은 우리 셋의 자리뿐.** 카드의 `editRequest` 스크립트, 요청 트리거, 프롬프트 보기 화면도 각 항목을 RisuAI 모양으로 따로 본다.
- **작가 노트**는 RisuAI의 자리(프리셋의 작가 노트 항목)에 간다. 챗이 SillyTavern식 깊이를 정했으면 그 깊이로 대화 기록 안에 들어간다.
- **프리셋의 글도 카드를 읽는다.** RisuAI처럼 프리셋의 매크로가 카드 설명·로어·챗 변수를 읽고, 카드의 `{{mainprompt}}`·`{{globalnote}}`·`{{jailbreak}}`가 프리셋의 글을 읽는다. 프롬프트 보기 화면은 언제나 열린다.

## 3. 캐시 규칙

오너 개발 계정으로 ChatGPT 경로에 실제 요청을 보내 확인한 규칙이다. **앞 요청에서 마지막 메시지만 뺀 부분을 저장해 두었다가, 다음 요청이 그 부분으로 통째로 시작할 때만 재사용한다.** 앞 요청과 공통인 앞부분이 아무리 길어도, 그 부분 전체가 아니면 0이다. `prompt_cache_key`와 `session_id` 헤더가 없으면 같은 요청을 두 번 보내도 0이다. Sol과 Astra 모두 명시적 캐시 지점(`prompt_cache_breakpoint`)을 거절하고 같은 규칙을 따른다. 저장된 프롬프트는 60분 뒤에도 통째로 재사용됐다(10·30·60분 모두 확인, 더 긴 간격은 재지 않음).

**지금 배치** (2.4만 토큰 대화, 200초 뒤 다음 턴, 24,750토큰 중 23,936 재사용):

| 요청 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| N번째 턴 | 시스템 | 대화 기록 | 입력 N | 묶음 N (마지막) | | |
| N+1번째 턴 | 시스템 | 대화 기록 | 입력 N | 답 N | 입력 N+1 | 묶음 N+1 |

N번째 요청에서 마지막 메시지(묶음 N)를 뺀 1~3이 저장되고, N+1번째 요청이 1~3으로 그대로 시작하므로 재사용된다.

**이번 턴 기억을 입력 앞에 두면** (실측 0):

| 요청 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| N번째 턴 | 시스템 | 대화 기록 | 기억 N | 입력 N (마지막) | | |
| N+1번째 턴 | 시스템 | 대화 기록 | 입력 N | 답 N | 기억 N+1 | 입력 N+1 |

저장된 1~3(기억 N까지)이 N+1번째 요청에 통째로 들어 있지 않아 재사용이 0이다. 시스템 프롬프트 안에서 키워드 로어가 바뀌는 것도 같은 이유로 0이 되어, 키워드 로어를 이번 턴 묶음으로 옮겼다.

### 그래도 캐시가 깨지는 경우

서버 로그의 `[cache]` 줄이 대화 응답마다 재사용 비율, 앞 요청과의 간격, 깨졌다면 그 이유를 남긴다(`apps/api/src/cacheHealth.ts`). 100회마다 이유별 합계도 찍는다.

| 원인 | 빈도 | 로그 이유 | 처리 |
|---|---|---|---|
| 요약이 들어오는 턴 | 64k에서 15~20턴에 한 번 | `summary_landed` | 몰아서 요약해 드물게 만들었다 |
| 카드 스크립트가 지난 답장을 고쳐 씀 | 해당 카드는 거의 매 턴 (Parma Knights 96%, 당나라 무협 100%) | `unknown`, `edited_or_regenerated` | 카드 설계라 둔다 |
| 트리거가 바꾼 변수가 시스템 글에 들어감 | 당나라 무협 35%, Parma 4~17%, 치트용사 0% | `system_changed:other` | 카드 설계라 둔다 |
| 작가 노트·깊이 로어 | 쓰는 카드는 매 턴 | `depth_injection` | RisuAI·ST 연출 그대로 둔다 |
| 편집·재생성·오래 쉰 뒤 | 독자 행동에 따라 | `edited_or_regenerated`, `gap_long` | 60분 쉰 뒤에도 통째로 재사용됨을 확인. `gap_long`은 60분이 넘은 경우만 |

### 캐시가 주는 이득

- **속도는 조금 빨라진다.** 캐시된 1만 토큰당 첫 글자가 약 0.17초 빨라진다(95% 구간 −0.03~0.40초, 5만 토큰 프롬프트로 67번 실측). 지금 배치는 5만 토큰 대화의 다음 턴에서 약 0.8초를 아낀다. 기다림 4~6초의 대부분은 캐시와 상관없이 제공자가 답을 보내기 시작하기까지의 2.7~3.7초다. 그래서 속도를 위해 캐시를 더 좇지 않는다.
- **요금제 사용량은 이 경로에서 잴 수 없다.** Codex가 사용량을 읽는 `x-codex-*` 응답 헤더가 이 경로에서는 오지 않았다. Codex 요금표는 GPT-6.1 Sol의 캐시된 입력을 일반 입력의 1/20 크레딧으로 적지만, 구독 사용량은 그것만으로 정해지지 않는다고 한다.

## 4. 요약이 도는 방식

RisuAI HypaV3 방식이다. 답이 끝난 뒤 백그라운드에서 돌고, 원문이 프롬프트에 다 들어가는 동안에는 요약하지 않는다. 64k 기본값에서는 약 290~350메시지까지 요약 없이 원문 그대로 간다.

### 요약이 들어오는 턴

| | 요약 | 이번에 요약할 메시지 | 원문 | 최근 3개 |
|---|---|---|---|---|
| 들어오기 전 (원문이 자리를 넘침) | 요약 1~3 (18메시지분) | 18메시지 | 7 | 3 |
| 들어온 뒤 (한 턴에 함께 반영) | 요약 1~6 (36메시지분) | 없음 | 7 | 3 |

- 6메시지가 요약 1개가 된다. 최근 3개는 요약하지 않는다.
- 한 번에 최대 12묶음(72메시지)까지 쓰고, 다 끝날 때까지 프롬프트에는 이전 상태를 보낸다. 그래서 요약 블록과 대화 기록의 시작이 한 턴에 한 번만 바뀐다.

### 64k 자리 나누기 (요약이 시작된 대화의 예)

| | 고정 | 기억 | 대화 원문 | 여유 | 답 |
|---|---|---|---|---|---|
| 요약 직전 | 8k | 12.8k | 42k | 0 | 1.2k |
| 요약 직후 | 8k | 12.8k | 35.6k | 6.4k | 1.2k |

- 기억 자리는 늘 컨텍스트의 20%(12,800토큰)다. 고정 부분(캐릭터, 로어, 이번 턴 묶음)은 작품마다 달라서 8k는 예시다.
- 원문이 넘치면 넘친 만큼에 컨텍스트의 10%(6,400토큰)를 더 요약한다(RisuAI 설정 `extraSummarizationRatio` 0.1). 그 여유가 다시 찰 때까지, 대략 15~20턴 동안 요약하지 않는다.

### 기억 자리 안에서 요약을 고르는 순서

| 순서 | 몫 | 보내는 자리 |
|---|---|---|
| 1 | 중요 표시한 요약 | 시스템 프롬프트 (요약이 들어올 때만 바뀜) |
| 2 | 최근 40% | 시스템 프롬프트 |
| 3 | 지금 대화와 비슷한 것 40% | 이번 턴 묶음 (매 턴 새로 고름) |
| 4 | 무작위 20% | 이번 턴 묶음 |

### 단계별

- **언제.** 답이 끝날 때마다 원문이 자리에 들어가는지 본다. 다음 독자 입력이 들어갈 자리까지 세어, 넘치기 한 턴 전에 요약한다.
- **무엇을.** 가장 오래된 6메시지를 요약 1개로 만들고, 여유가 생길 때까지 묶음을 이어 쓴다. 요약을 다시 요약하지 않고 언제나 원래 메시지로 만든다.
- **누가, 어떻게.** 보조 모델이 RisuAI 요약 프롬프트로 쓴다. 프롬프트가 실제로 보내는 글(카드 스크립트가 지운 상태창은 빠진 글)을 읽고, 성인 등급 픽션이니 거르지 말라는 지시를 붙인다.
- **거절하면.** "도와드릴 수 없습니다" 같은 답은 요약으로 저장하지 않는다. 그 구간을 비워 두고 10분 뒤 다시 시도한다.
- **바로 이어서.** 같은 묶음에서 사실을 뽑고, 바뀐 옛 사실은 종료한다. 요약과 사실은 KURE로 임베딩해 "비슷한 것" 찾기에 쓴다.
- **시간 표기.** 요약과 사실 앞에 "(약 40턴 전)"을 붙인다. 이 숫자는 요약이 들어오는 턴에만 갱신해 그 사이에 시스템 프롬프트를 흔들지 않는다.
- **고치거나 지울 때.** 요약은 덮은 메시지 목록을 들고 있어 그 브랜치에서만 쓰인다. 덮은 메시지를 고치면 요약과 그 사실이 같이 지워지고, 빈 구간을 먼저 다시 요약한다. 카드 스크립트가 첫 메시지를 바꿔 대화들의 첫 인사가 바뀔 때도 같다 — 스크립트가 돈 대화는 곧바로, 다른 대화는 제 다음 정리 때 다시 요약한다.
- **비용.** 요약하는 총량은 몰아서 하든 아니든 같다. 묶음마다 보조 모델을 2번(요약 1번, 사실 1번) 부르고, 그 호출이 15~20턴마다 한꺼번에 몰린다.

## 5. 로어북

켜지는 항목은 RisuAI·ST 규칙 그대로다. RisuAI 책은 RisuAI 코드가 읽는 데코레이터를 모두 읽고(`@@depth`·`@@reverse_depth`·`@@position`·`@@role`·`@@inject_*`·`@@activate_only_every`·`@@is_greeting`·`@@priority`·`@@match_full_word` 등), 책이 정하지 않으면 RisuAI처럼 최근 5개 메시지를 훑고 재귀로 켠다. 같은 순서값의 항목은 RisuAI처럼 뒤집힌 순서로 놓인다. 바뀐 것은 키워드로 켜진 항목을 보내는 자리와, 예산을 정하지 않은 RisuAI 책의 예산이다.

### 보내는 자리

| 항목 | 자리 |
|---|---|
| 키워드·재귀·sticky로 켜진 항목 중 기본 자리(RisuAI 기본 슬롯, ST ↑Char/↓Char)에 있던 것 | 이번 턴 묶음의 맨 앞 |
| 상시 로어, 카드가 `@@position`으로 자리를 정한 항목 | 시스템 프롬프트 그대로 |
| 깊이 로어, 작가 노트 슬롯, 예시 슬롯, outlet, `@@inject_*`나 system 아닌 `@@role`을 단 항목 | 원래 자리 그대로 |

RisuAI 책의 `@@depth N`은 RisuAI의 실제 코드대로 대화 기록의 **가장 오래된** 메시지부터 N번째 자리에 들어가고(V3 명세는 끝에서 센다고 적지만 RisuAI는 그렇게 하지 않는다), `@@reverse_depth N`은 끝에서 N번째, 깊이 0과 `@@end`는 맨 뒤다. 카드의 `depth_prompt`와 ST 책의 깊이는 ST처럼 끝에서 센다.

프롬프트 보기 화면에는 "로어북 (키워드로 켜진 것)"이 따로 보인다. `@@position` 표시(`LoreEntry.positioned`)는 2026-10-16에 생겼으므로, 그 전에 가져온 카드는 다시 가져와야 자리를 정한 항목이 시스템 프롬프트에 남는다.

### 예산 (로어가 쓸 수 있는 최대치)

| 경우 | 예산 |
|---|---|
| 카드가 예산을 정함 | 그 값 (Realm 카드 12장 중 11장) |
| 정하지 않은 RisuAI 책, 스튜디오에서 쓴 책 | 컨텍스트의 50% (64k에서 32,000) |
| 정하지 않은 ST 책 | ST와 같은 25% (답 자리를 뺀 컨텍스트 기준) |

RisuAI 자체의 기본은 8,000이다(빈 설정은 800이지만 시작 때 마이그레이션이 8,000으로 올린다). 카드 내용을 자르는 상한은 버그라는 원칙(AGENTS.md)으로 50%까지 올렸다. 예산은 넘지 못하는 선일 뿐이라, 로어가 덜 쓰면 남는 자리는 대화 기록이 쓴다.

## 6. 숫자로 본 효과

"실측"은 오너 개발 계정으로 실제 ChatGPT에 보낸 결과다. 나머지는 실제 카드와 대화로 계산한 값이다.

### 연속 턴에서 재사용된 프롬프트 (실측)

| 비교 | 다른 배치 | 지금 |
|---|---|---|
| 이번 턴 기억의 자리 (2.4만 토큰 대화) | 입력 앞 0% | 입력 뒤 96.7% |
| 키워드 로어의 자리 (당나라 무협 1.9만 토큰, 카드 Lua 끄고) | 시스템 0% | 입력 뒤 65% |

당나라 무협은 실제로는 카드 Lua가 매 턴 지난 답장을 고쳐 써서 어느 배치든 캐시가 깨진다. 위 숫자는 로어 자리의 효과만 본 값이다. (`data/evals/cache/`, `data/evals/prompt-structure/`)

### 캐시와 첫 글자 (실측)

약 5만 토큰 프롬프트에서 캐시된 양만 바꿔 단계마다 6번씩, 섞인 순서로 보냈다(GPT-6.1 Sol, 기본 추론, 67번).

| 캐시된 토큰 | 0 | 9,856 | 24,704 | 39,680 | 48,640 |
|---|---|---|---|---|---|
| 첫 글자까지 중앙값 | 5.26초 | 5.87초 | 6.31초 | 5.38초 | 4.90초 |

- 캐시된 1만 토큰당 **0.17초** 빨라진다(95% 구간 −0.03~0.40초). 같은 요청도 4.1~10.9초로 흔들려, 차이가 흔들림보다 작다.
- 기다림의 대부분은 제공자가 답을 보내기 시작하기까지의 2.7~3.7초이고, 이것은 캐시와 상관없다.
- GPT-6 Astra는 0과 4.9만 토큰에서 차이가 없었다(5.05초 대 5.39초).
- 그래서 지금 배치는 그대로 두되(턴마다 드는 비용이 없다), 속도를 위한 캐시 작업은 여기서 멈춘다. 요금제 사용량에 대한 효과는 이 경로에서 잴 수 없다.

### 키워드 로어가 바뀌는 턴의 비율

Realm 카드 6장, 카드마다 40~62메시지 한국어 대화. 시스템 프롬프트에 두면 이 비율만큼 캐시가 깨졌다. 바뀐 항목은 전부 기본 자리였다.

| 카드 | 바뀐 턴 |
|---|---|
| 치트용사 | 100% |
| 당나라 무협 | 100% |
| 성배전쟁 | 84% |
| 여인무림 | 72% |
| 아카데미아 | 65% |
| Parma Knights | 4% |

### 키워드 로어를 입력 뒤로 옮겨도 답이 괜찮은가 (실측)

로어를 알아야 답할 수 있는 장면 14개를 두 배치로 생성하고, 전체 프롬프트를 보여 주며 양쪽 순서로 판정했다.

| 판정 | 입력 뒤 승 | 시스템 승 | 무승부 |
|---|---|---|---|
| 모델 판정 28회 | 7 | 3 | 18 |
| 블라인드 직접 판정 14회 | 1 | 1 | 12 |

로어 사실을 맞게 쓴 정도는 28회 모두 같았고, 상관없는 로어를 끌어다 쓴 답은 양쪽 다 0개였다. 규칙으로 적힌 로어 7개도 양쪽 모두 지켰다.

### 요약을 몰아서 할 때

메모리 실험 대화 2개를 16k로 다시 돌린 값. 64k에서는 차이가 더 커질 것으로 보지만 아직 재지 않았다.

| 지표 | 매번 요약 | 몰아서 요약 |
|---|---|---|
| 연속 턴에서 시스템과 대화 기록이 그대로인 비율, 대화 1 | 48% | 81% |
| 같은 비율, 대화 2 | 51% | 65% |
| 기억 질문 300개의 답이 프롬프트에 들어 있던 수 | 300 | 299 |

### 예산을 정하지 않은 RisuAI 책 (Parma Knights, 25턴)

| 핵심 상시 항목 | 25% | 50% |
|---|---|---|
| 호감도 시스템이 들어간 턴 | 5/25 | 25/25 |
| 위치 시스템이 들어간 턴 | 1/25 | 21/25 |
| 대화 기록과 기억에 남는 자리 | 약 4.4만 토큰 | 약 2.8만 토큰 |

대화 49개는 양쪽 다 전부 들어갔다. 답 품질 차이는 아직 재지 않았다.

### 기본 컨텍스트 64k

16k와 비교해 답은 같거나 조금 나았다. 프롬프트가 길어진 만큼 첫 글자가 늦어지는 것은 캐시되지 않은 1만 토큰당 0.2초 안팎이다(위 캐시와 첫 글자).

### 영어 작품의 로어가 한국어 대화에서 걸리는가

Realm 카드 4장, 한국어 160턴. F1, 1에 가까울수록 정확하다.

| 방법 | F1 |
|---|---|
| 영어 키만 사용 | 0.07 |
| 조정한 의미 검색 | 0.42 |
| 작가가 직접 단 한국어 키 | 0.78 |
| 한국어 별칭 자동 생성 (채택) | 0.90 |

### 뜻 검색에 글자 검색(BM25)을 합친 효과

| 찾는 것 | 뜻만 | 합침 |
|---|---|---|
| 과거 메시지, 이름·숫자로 다시 언급 | 36% | 87% |
| 과거 메시지, 다른 말로 바꿔 언급 | 14% | 61% |
| 사실, 이름·숫자로 다시 언급 | 85% | 100% |

### 기억이 틀린 내용을 덜 보내는가

사실이 바뀌는 사건 23개. 낮을수록 좋다.

| 지표 | 쌓기만 | 지금 |
|---|---|---|
| 이미 틀려진 옛 사실이 모델에 들어감 | 68% | 11% (종료 표시) |
| 옛 사실과 새 사실이 같이 들어감 | 42% | 11% |
| 그룹: 없던 장면의 비공개 사실이 들어감 | 13% (전체 공개) | 0% (멤버별) |

## 7. 레퍼런스

- **호환 대상: 그대로 따라 한다.**
  - **RisuAI**: 카드 형식(charx), CBS, Lua 트리거, 모듈과 토글, HypaV3 요약, 로어 규칙과 예산. 한국 커뮤니티 작품(Realm)이 대부분 여기서 나온다.
  - **SillyTavern**: 월드 인포 규칙(재귀·예산·sticky), 매크로, 정규식 배치, 메시지 검색, 채팅 브랜치와 추론 표시.
- **캐시와 순서의 참고.** RisuAI·ST는 캐시가 생기기 전에 설계돼 매 턴 바뀌는 로어와 기억을 앞쪽에 둔다. 그 자리는 따르지 않고 항목만 따른다.
  - **Codex**: 같은 ChatGPT 경로를 쓰는 OpenAI의 도구. 요청 뒤에 덧붙이기만 하고 압축은 드물게 크게 한다. 캐시 이름과 `session_id` 헤더, 드문 요약의 근거다.
  - **PocketRisu**: 서버에서 답을 끝까지 받아 두는 방식. 화면을 닫아도 답이 저장되는 근거다.
- **기억의 참고 (지금도 활발한 것).** AI Dungeon(몇 액션마다 요약), mem0(사실 추출; 한국어 글자 검색이 조용히 실패해 우리가 감시 지표를 둔 계기), Open WebUI(뜻·글자 검색 합치기).
- **연구.** LongMemEval·LoCoMo(시간 정보가 큰 차이), MOOM(6턴마다 요약), CareCall·KEEM(기억은 갱신이 낫다), REVERIEMEM(사실마다 누가 아는지).
- **무시 (활발하지 않음).** superbooga·superboogav2, long_term_memory, Letta V1 서버와 MemGPT 구조.

## 8. 결정과 이유

원칙: 호환에 필요한 복잡함은 받아들이고, 우리가 더하는 것은 숫자로 이득이 확인될 때만 남긴다.

### 프롬프트와 캐시

| 결정 | 상태 | 이유 |
|---|---|---|
| 이번 턴에만 쓰는 것은 독자 입력 뒤 한 메시지로 | 적용 | 실측 재사용 0% → 96.7%, 12개 장면에서 품질 차이 없음 |
| 키워드로 켜진 로어도 입력 뒤로 | 적용 | 로어 많은 카드에서 65~100% 턴마다 바뀜. 14개 장면에서 품질 같음, 재사용 0% → 65% |
| 대화마다 캐시 이름과 `session_id` 헤더 | 적용 | 없으면 같은 요청도 재사용 0. `session_id` 하나로 충분함을 실측 |
| 캐시가 깨진 이유를 로그로 | 적용 | 진단용으로 둔다. DB에는 쓰지 않는다 |
| 속도를 위한 캐시 작업은 여기서 멈춤 | 적용 | 캐시된 1만 토큰당 첫 글자 0.17초(많아야 0.4초). 기다림의 대부분은 캐시와 상관없는 제공자의 시작 지연이다 |
| 최근 켜진 로어를 시스템에 묶어 두기, 동점 항목을 책 순서로 | 쓰지 않음 | 재사용은 늘지만(치트용사 턴당 21k → 9~11k 토큰 새로 읽음) 12개 장면에서 장면이 떠난 로어를 끌어온 답이 1개 나왔고 나아진 답은 없었다. 이득은 첫 글자 속도뿐이고 그것도 턴당 0.17초(많아야 0.4초)로 쟀다. 동점 순서는 이 방식에서만 의미가 있어 함께 두지 않는다 |

### 기억

| 결정 | 상태 | 이유 |
|---|---|---|
| 기본 컨텍스트 64k | 적용 | 약 290~350메시지까지 요약 없이 원문. 답은 같거나 조금 나음 |
| 요약은 몰아서, 드물게 (`extraSummarizationRatio` 0.1) | 적용 | 연속 턴 안정 비율 48% → 81%, 기억 회상 그대로 |
| 요약에 성인 등급 지시, 거절은 저장하지 않음 | 적용 | 거절 문구가 요약으로 굳으면 그 구간을 잃는다 |
| 요약 단위 6메시지, 계층 요약·30메시지 단위·HypaPlus 형식은 쓰지 않음 | 쓰지 않음 | 상위 요약도 옛 사건 정답률 93%로 같았다 |
| 사실은 지우지 않고 종료 표시, 그룹은 멤버별 | 적용 | 틀린 옛 사실 68% → 11%, 없던 장면의 비밀 0% |
| 모델이 읽는 우리 글은 영어 (PocketRisu처럼) | 적용 | PocketRisu와 같게 하려는 소유자 결정. 한국어 시스템 프롬프트를 영어로 바꾼 비교에서 이득은 확인되지 않았고, 지금의 영어 지시가 답장 언어·거절률·글의 질에 주는 차이는 아직 재지 않았다 |

### 로어와 검색

| 결정 | 상태 | 이유 |
|---|---|---|
| 예산을 정하지 않은 RisuAI 책은 50% | 적용 | 카드 내용을 자르는 상한은 버그. Parma 핵심 항목이 25턴 내내 들어감 |
| 다른 언어 로어는 한국어 별칭으로, 의미 기반 로어북은 쓰지 않음 | 적용 | 별칭 F1 0.90, 의미 검색 0.42 |
| 임베딩은 KURE-v1 하나, 뜻·글자 검색을 합침 | 적용 | 이름·숫자 재언급에서 과거 메시지 찾기 36% → 87% |
| KURE-v1의 공개 변환본(Hugging Face, 2026-10-18) | 쓰지 않음 | 같은 글의 벡터가 우리 변환과 평균 0.978로 갈렸고, 기억 평가에서 비슷한 요약 찾기(바꿔 말한 질문) 57% → 54%, 과거 메시지 찾기 90% → 85%. 그래서 우리 변환을 Hugging Face에 올렸고(2026-10-19, `rokrokss/KURE-v1-onnx`), 설치판(`npx shizue-plot`)은 처음 시작할 때 그것(약 740MB)을 배경에서 받는다. 다 받기 전까지는 뜻 검색 없이 돈다 |
| 재순위 모델 | 쓰지 않음 | 모델에 들어가는 내용이 거의 바뀌지 않았고(요약 블록 91개 중 0개) 시간과 메모리가 더 든다 |

## 9. 용어

| 용어 | 뜻 |
|---|---|
| 캐시 | 앞 요청과 앞부분이 같으면 모델이 다시 읽지 않고 재사용하는 것. 이 경로는 앞 요청에서 마지막 메시지만 뺀 것을 통째로 재사용한다 |
| 이번 턴 묶음 | 독자 입력 뒤에 붙는 한 메시지. 매 턴 새로 만드는 로어, 지시, 기억을 모은다 |
| 캐시 이름 (`prompt_cache_key`) | 요청에 붙이는 이름. 대화 id를 써서 같은 대화끼리 캐시를 찾게 한다 |
| 첫 글자까지 걸린 시간 | 요청을 보내고 답의 첫 글자가 나오기까지의 시간. 캐시된 1만 토큰당 약 0.17초 짧아진다 |
| 로어북 (월드 인포) | 작품의 설정 사전. 대화에 특정 단어가 나오면 그 설정을 모델에게 알려 준다 |
| 상시 로어 | 키와 상관없이 늘 들어가는 로어 항목 |
| 작가 노트 · 깊이 로어 | 대화 기록 중간, 예를 들어 끝에서 4번째 메시지 자리에 끼워 넣는 글 |
| 로어 예산 | 로어가 프롬프트에서 쓸 수 있는 최대 토큰. 넘치면 순서가 뒤인 항목부터 빠진다 |
| 별칭 | 영어 키의 한국어 이름. 자동으로 만들고 원래 키는 건드리지 않는다 |
| HypaV3 | RisuAI의 장기 기억 방식. 밀려난 대화를 요약해 두고 중요·최근·비슷한 것·무작위로 골라 넣는다 |
| 요약이 들어오는 턴 | 새 요약이 프롬프트에 처음 반영되는 턴. 요약 블록과 대화 기록 시작이 바뀌어 캐시가 깨진다 |
| 사실 블록 | 요약에서 뽑은 짧은 사실 목록. 바뀐 사실은 종료 표시한다 |
| 임베딩 · KURE-v1 | 문장을 숫자 좌표로 바꿔 뜻이 가까운 것을 찾는 방법과, 우리가 쓰는 한국어 모델 |
| BM25 | 드문 글자 조각이 겹치는지로 찾는 고전 검색. 이름과 숫자에 강하다 |
| 모델 프리셋 | 어느 형식(Chat Completions·Responses·Anthropic·Gemini, 그리고 Vertex·Bedrock·Mistral·Cohere·Ollama·Kobold·NovelAI·Horde 같은 RisuAI의 나머지 형식)으로, 어느 키나 주소로, 어떤 모델에 어떤 값(온도, 추론 강도 등)을 보낼지 묶은 것. PocketRisu의 모델 프리셋이다. 레지스트리 프로필로 만든 것은 그 모델이 받는 칸만 보낸다 |
| 모델 레지스트리 · 프로필 | PocketRisu가 관리하는 모델 목록. 프로필 하나가 모델 하나이고, 보낼 칸·기본값·응답 상한·컨텍스트 창·상태(현재·구형·지원 종료)를 정한다. 이 버전에 사본이 들어 있고 설정에서 새로 받는다 |
| 보조 모델 | 요약, 사실 추출, 별칭, 번역 같은 뒷일을 맡는 모델. 챗의 보조 프리셋이고, 비면 설정의 기본 보조, 그것도 비면 메인 모델이다 |
| CBS · 매크로 | 카드 안의 `{{...}}` 문법. RisuAI는 CBS, SillyTavern은 매크로라고 부른다 |
| 트리거 · Lua | 카드가 넣은 프로그램. 변수를 바꾸거나 요청과 답을 고친다 |
| Realm | RisuAI 작품 공유 사이트. 실험과 호환성 점검에 실제 카드를 쓴다 |
